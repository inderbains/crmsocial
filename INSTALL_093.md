# Fix 093 — Brokerage details first, email activation, then password

Prepared from the saved Version 9 / Fix 091 sources. No live GitHub or Supabase access. This patch changes the public registration entry and adds a self-contained activation view on the existing homepage route. It does not require `/brokerage-setup/` to be deployed. Existing brokerage and agent records are not changed by installation. No Stripe or SMTP changes.

## 1. Supabase (crmsocial, staging first)
- If 091 was not applied, run the included `supabase/091_brokerage_registration.sql` (whole contents). It creates the existing verified-account RPC used here. Requires the platform tables installed by 084/088, and existing brokerage/agent schema. It is safe to rerun if the original 091 is already installed; it replaces that RPC and revokes the legacy creation RPC. 
- Run `supabase/093_brokerage_preflight.sql`. It checks eligibility before a password is changed; it does not create or change memberships.
- Authentication → URL Configuration → Redirect URLs: add exactly `https://beige-pelican-746269.hostingersite.com/?rv_brokerage=activate` (adjust to the real deployed origin if it changes). Preserve other redirects. Confirm Email must be enabled. The confirmation email template must use the normal `{{ .ConfirmationURL }}` link. This patch uses the browser-only implicit auth flow; a custom PKCE/token-hash callback is not supported by this view. Do not paste authentication links in chat.

## 2. GitHub
- Upload `app/page.tsx`, `components/rv-marketing/BrokerageActivation.tsx`, `components/rv-marketing/BrokerageActivation.module.css` and merge the registration CTA/modal changes in `components/rv-marketing/MarketingLanding.tsx` into the latest repository. Do not overwrite unrelated newer edits in MarketingLanding. Build (`npm run typecheck`, `npm run build`) and deploy on Hostinger. Verify the new view before sending registration emails: `https://beige-pelican-746269.hostingersite.com/?rv_brokerage=register`.
- Fix 092 is still the agent invitation implementation. It is not replaced here. Ensure the 092 SQL, `app/accept-invitation/` files and updated `agent-office` Edge Function are actually deployed. See original Fix 092 instructions. Use fresh links only. This patch does not send agent invitations until the brokerage is established.

## 3. Test
1. New browser, new email. Select Brokerage. Enter brokerage name, administrator name and email, then send email. No user-selected password is collected yet. Supabase stores the pending signup details in Auth user metadata and sends the standard confirmation email. That metadata is not an authorization source for roles.
2. Click the link. It should open the root activation view with Continue to create password. The activation view uses only credentials from that link, not the previous browser account. Verify details, set password, confirm. The 091 RPC creates the brokerage, admin membership and profile atomically. The normal workspace is opened only after checking exact user ID, role and brokerage ID. Back Office should appear; verify it and check Super Admin. Test with another account already logged in, expired/reused link, existing agent, pending invitation and platform owner. No automatic changes to existing membership are permitted.
3. For the existing verified account `sell@inderbains.ca`, visit the registration view, choose Already verified an account? Finish brokerage setup, enter that account's current password, enter office details and confirm current password. This is only allowed if it is unassigned and passes 091/093 server checks. It does not create a duplicate login.
4. Invite an unused email via Back Office → Agents. Test Fix 092 activation (locked email and brokerage, password creation, accepted agent role, private workspace). Confirm that prior sessions and other brokerage data are not accessible.

## Limitations
- Source-level tests and syntax transpilation only; no full dependency-backed typecheck/build or live Auth callback/SQL tests here. The actual deployed branch is not verified. Test on staging before real customers.
- Standard confirmation links can be consumed by email scanners; if that happens, use a fresh link or a later dedicated token-hash confirmation flow. If activation is interrupted after the password is set but before brokerage creation, use the existing verified-account recovery option. If interrupted after brokerage creation, log in normally. If the email was verified but password not yet set, use the ordinary password recovery workflow and then finish setup. No browser session should be accepted as proof of link identity.
- Self-service signup is not brokerage licensing verification. No paid subscription, additional admins or agent memberships are created here. Existing database privacy controls still need independent live testing.
