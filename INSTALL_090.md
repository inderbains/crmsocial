# Fix 090 — Scoped deletion controls (no Stripe)

Requires Fix 089 (and 084–086/088). This is an incremental patch for your disposable test environment, not a production erasure workflow. Back up database and files and test in staging first. Stop ordinary application traffic during destructive testing.

1. Open `supabase/090_scoped_test_deletion.sql` and copy the entire SQL into the same crmsocial project's SQL Editor. Run. Installation changes functions only; it deletes no accounts or data.
2. Upload the three replacement files from `app/admin/` to their matching GitHub paths. Keep existing admin CSS and management panel from Fix 089. Run `npm run build` and deploy. No new Edge Function, secrets or Stripe.
3. Sign in to `/admin/` and refresh. Every brokerage has its own **Delete brokerage** button. Every unprotected registered account has **Delete**. Pending invitations have **Cancel invitation**. A visible modal asks you to type the name/email exactly and displays the database error if the operation fails.
4. Delete an empty test brokerage: removes its reviewed setup records, memberships and invitations, but **keeps its registered login accounts and private user data**; they appear as unassigned afterward. The owner stays protected. Delete individual unused test accounts separately. If removing the last administrator, delete the empty brokerage first or appoint another administrator. The office audit records for setup-only events are removed for the selected disposable brokerage; financial or other audit history blocks deletion. Platform audit history remains. A pending invitation cancellation does not delete an existing login or revoke an already issued magic link; it removes the invitation record so the hardened acceptance RPC cannot assign that invitation to a brokerage.
5. Direct deletion is scoped to the selected test identity or brokerage, not to the presence of unrelated records across the database. Related business records, matching stored files, reviewer assignments or other dependencies still block it. If blocked, do not disable constraints, RLS or bypass safeguards. For the explicitly disposable old test environment, use the earlier reviewed full reset after backup and Storage cleanup. Do not run this on production customer records.
6. Test in staging with two unrelated brokerages: verify deletion of an unused agent and empty brokerage with unrelated records present, cancellation of a pending invitation, refusal to delete the protected owner and last admin, refusal to delete a brokerage with transaction/financial records or uploaded files, and correct directory counts after deletion. Verify unrelated user data is unchanged. Test RPCs with ordinary agent/admin tokens and expired owner verification; all destructive actions must fail. SQL and live Auth/Storage integration must be tested; source checks alone are not enough. Existing JWTs may remain valid until expiry; this is not full suspension/forced logout. Storage scanning checks recorded object ownership and UUID path components, not every possible external file or undocumented reference. Unknown live schema dependencies may block deletion. No live changes have been made by this package.
