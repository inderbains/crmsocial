# Fix 094 — clickable agent invitation and password activation
Requires installed Fix 092 SQL and Fix 093 homepage files. Staging first. This patch uses the existing homepage with `?rv_agent=activate&invite=...#token_hash=...`. The token remains in the fragment, is exchanged only after a deliberate click, and is not logged by this code. The email includes an HTML anchor and plain-text alternative. The invited email is the username, not an editable identifier.

1. Run the contents of `supabase/094_require_invited_password.sql` in SQL Editor. It replaces the 092 acceptance functions with a password-existence check. Do not run if 092 prerequisites are absent. No user data is deleted.
2. Upload `app/page.tsx`, `app/accept-invitation/page.tsx` and `app/accept-invitation/activation.module.css` to GitHub in the corresponding folders. Keep the 093 BrokerageActivation and MarketingLanding files. Merge unrelated newer edits. Confirm deployment completes. Open `/?rv_agent=activate` without token: expect Invitation unavailable, not homepage.
3. In Supabase > Edge Functions > agent-office > Code, replace the index.ts with the supplied full file (or merge if there are newer unrelated changes), then click Deploy. Confirm the updated timestamp. Keep JWT validation and existing secrets. APP_URL must be the current HTTPS site base. No email provider changes required. This is separate from GitHub.
4. Cancel/review the old pending invitation and stale Auth user through authorized admin tools; do not delete unrelated accounts. For the first test use a never-registered email. Old magic links cannot be made safe retroactively by changing the mail template; revoke affected sessions and old invitation tokens through authorized Auth administration as appropriate. Do not reuse the exposed link. Fresh invitation should contain an actual clickable button, not the old `?onboard=` URL.
5. Open the fresh email in a private window. Click Accept invitation & create profile, then Continue to create account. Verify assigned brokerage and email; create a matching password (12+ characters), accept terms, and open dashboard. Confirm login with that email/password after sign-out. Repeat while another account is signed in, with expired and mismatched links, and confirm no old workspace opens. Check wrong-brokerage and direct API access.

Scope: the UI keeps verification session isolated and the acceptance SQL rejects missing password hashes, but this does not independently prevent every API request by a pending Auth identity; a full backend pending-account access audit is still required. An already activated or legacy unlinked account cannot be silently reassigned. Source checks and syntax checks only; no live SMTP, Supabase or production Next build verified. This patch preserves the existing Stripe office billing branch; it does not enable Stripe.
